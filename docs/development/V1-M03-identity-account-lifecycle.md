24 October 2026 safe account-switch presentation: added a dedicated GetX controller and responsive confirmation screen for the uncommon multi-account case while retaining the one-account-per-device default experience. Pending records block switching offline; online pending records require an explicit sync-first action; synchronization is rechecked before suspension; residual changes keep the existing account active. Only a fully prepared state clears decrypted runtime state, preserves encrypted recovery material and invokes navigation to authenticate another account. The screen explains these boundaries and never describes switching as deletion or sign-out. Static analysis is clean and all nine focused controller, domain and secure-adapter tests pass. Authenticated-shell navigation, live connectivity/sync and production auth entry remain pending.

24 October 2026 account and data safety screen: added a responsive GetX controller/UI that keeps Sign Out, Clear Local Data and Delete Account visibly and behaviorally separate. Sign Out detects protected pending records, distinguishes offline blocking from an online sync-first choice, and navigates away only after account files, keys and session state are safely cleared. Clear Local Data requires confirmation, refuses to destroy pending records and explicitly keeps the user signed in. Delete Account requires separate destructive confirmation, surfaces recent-authentication, pending-sync, server-rejection and local-cleanup-pending states, and supports an injected reauthentication-and-retry action without treating cancellation as deletion. No failure path claims data was removed. Static analysis is clean and all 21 focused presentation and lifecycle tests pass. Authenticated-shell navigation, live connectivity, synchronization and provider reauthentication adapters remain pending.

24 October 2026 account-access presentation: added a responsive GetX sign-in/account-creation screen and controller over the existing backend-neutral contracts. The flow supports password sign-in, Google entry, adult self-attestation without identity documents, email-verification state, resend/check actions when adapters are available, enumeration-safe password recovery, busy/error states and encrypted-runtime activation only for a ready verified adult identity. Under-18 registration performs no backend write and shows a respectful V1 eligibility exit; unverified accounts never open local account storage; raw provider errors are never rendered. The UI remains separate from the current onboarding preview until a trusted provider adapter and project identifiers exist, so it cannot falsely claim account creation. Static analysis is clean and all 23 focused presentation, sign-in, registration, verification, recovery and activation tests pass. Provider SDK integration, token validation, deep links and authenticated navigation remain pending.

22 October 2026 recent-reauthentication contracts: added provider-neutral password and Google reauthentication use cases for sensitive actions such as Delete Account. They operate inside the stable identity session, require the selected provider to already be linked, treat passwords as transient bounded input, distinguish Google cancellation from success, and reject backend results that change UID, verification, adult eligibility or provider linkage. Five focused tests cover valid password flow, input rejection, unlinked providers, cancellation and continuity attacks. Provider credential prompts and server-side recent-auth timestamps remain adapter responsibilities.

22 October 2026 Clear Local Data runtime continuity: separated same-account local reset from the destructive storage removal used by Sign Out and Delete Account. After the durable outbox gate passes, Clear Local Data deletes the old encrypted database and protected key, then creates and opens a fresh empty encrypted database for the still-authenticated owner. A file-backed integration test proves old records are absent, a protected key/file exist and the runtime remains bound to the same UID; adapter tests prove lifecycle operations call their distinct paths.

22 October 2026 authenticated deletion boundary: refactored deletion checks into a reusable owner coordinator and added a serialized-identity use case. Delete Account now rejects absent, unverified or adult-ineligible identity before side effects, waits behind in-flight account work, retains identity for reauthentication/synchronization/retry outcomes, and clears the usable identity only after cloud acceptance, atomic local cleanup and authentication-session clearing all succeed. Five focused tests supplement the six existing deletion/clear-data tests.

22 October 2026 authenticated sign-out boundary: intentional sign-out now obtains its owner from the serialized identity session rather than accepting a presentation-supplied UID. It waits behind in-flight owner work, preserves identity when offline/pending data or the atomic cleanup gate blocks removal, and publishes signed-out state only after local account cleanup and authentication-session clearing succeed. Five tests cover absent identity, offline blocking, successful cleanup, concurrency ordering and failed final cleanup.

22 October 2026 fail-closed auth transition: a runtime activation or suspension error now clears the usable in-memory identity before the original error is rethrown. Account-scoped operations therefore cannot remain authorized against an uncertain encrypted-runtime state. A later trusted event can recover normally. Two tests cover activation failure/recovery and a partial suspension failure after database closure, extending the integrated transition suite to six cases.

22 October 2026 provider-neutral auth stream binding: added a single-owner subscription bridge from a future validated provider stream into the trusted-auth coordinator. Delivered identity events reconcile in arrival order; shutdown cancels undelivered events and drains accepted work; duplicate starts are rejected; listener failures cannot poison later delivery. Transport errors are surfaced but deliberately do not invent a sign-out—only an explicit null identity revokes the local session. Four tests cover ordered activation/revocation, transient stream failure, draining shutdown and listener isolation. Provider-specific token validation remains pending.

22 October 2026 atomic trusted-auth transition: joined serialized identity ownership and encrypted-runtime reconciliation behind one ordered coordinator. Authentication loss now waits for in-flight owner work before closing its database; successful sign-in publishes the identity only after runtime activation; verification/adult-gated identities remain available to their restricted completion flows without opening account data; and an unexpected UID event suspends the old runtime and clears the usable identity. Four integration-style domain tests cover these boundaries. A production auth adapter must still validate tokens before submitting events.

22 October 2026 stable identity-session serialization: added the in-memory coordination boundary required by `StableIdentitySession`. Account-scoped work captures one trusted identity for its complete awaited operation; sign-out and account switching queue behind in-flight work, while later work observes the cleared or replacement identity. Failures do not poison the queue. Four concurrency tests cover sign-out ordering, account switching, post-failure recovery and rejection after authentication loss. This component coordinates identity state only; it does not persist credentials or replace server-side token validation.

22 October 2026 serialized auth-state reconciliation: authentication events are now queued through one coordinator instead of being allowed to overlap. A rapid second identity event waits for the first activation to finish, then the existing cross-account rule suspends the old runtime and blocks implicit activation of the new UID. A failed event completes with its error without poisoning the queue, so later trusted auth state can still be reconciled. Two race/error tests extend this area to six focused tests; provider SDK stream wiring remains pending on approved cloud identifiers.

22 October 2026 safe account-switch preparation: added an explicit pre-authentication workflow for changing accounts. Pending data blocks switching offline; online switching requires an explicit sync-first choice, then rechecks the durable queue before suspending the previous encrypted runtime. Successful preparation retains the old encrypted file/key for recovery but clears decrypted state; only then may the new authentication flow begin. Four domain tests and one composition test cover no-active, offline/online warnings, successful sync/suspend and residual pending data. Account-switch UI remains pending.

22 October 2026 auth-state reconciliation: added a coordinator for trusted auth-state events. A ready identity activates once; auth loss, verification downgrade or eligibility downgrade suspends the active encrypted runtime and clears memory. An unexpected different UID suspends the old owner but deliberately does not open the new one, returning `accountSwitchBlocked` until the explicit safe-switch flow resolves pending data. Four focused tests cover activation/idempotence, auth loss, gate downgrade and cross-UID events. Auth SDK stream subscription remains pending.

22 October 2026 auth-loss suspension: added a workflow for token expiry, revocation or unexpected auth-state loss. It closes the active encrypted database, always clears decoded/in-memory account state even if close fails, and verifies the runtime is inactive. Unlike a completed intentional sign-out, suspension preserves the encrypted file and protected key for same-account reauthentication and pending-record recovery. Four domain tests plus a file-backed encrypted recovery integration test pass. Auth SDK listener wiring remains pending.

22 October 2026 encrypted runtime adapter: connected the account activation gate to the real `AccountDatabaseService`. The adapter derives active UID directly from the database service instead of duplicating session state, opens the encrypted owner file only after access gates pass, reflects cleanup immediately, and refuses cross-owner activation. Two file-backed encrypted integration tests cover activate/cleanup and attempted account switching. Platform-device verification remains deferred.

22 October 2026 account-runtime activation gate: added a coordinator between sign-in and encrypted local storage. Verification-required and adult-eligibility-required identities cannot activate a database. Ready identities open only their requested UID; repeated same-owner activation is idempotent, direct cross-UID switching is blocked until safe sign-out, and the runtime must prove it published the requested owner after opening. Four focused tests cover these boundaries. The production runtime adapter and auth-state listener remain pending.
