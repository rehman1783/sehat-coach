# V1-M08 Monetization and entitlements

## Current evidence — 25 October 2026

The first platform-neutral entitlement and credit contract is implemented locally. Entitlement snapshots are explicitly server-verified, revisioned and time-bounded. Active access and bounded offline grace are distinguishable, while an online client with an expired snapshot must refresh rather than trusting stale access.

Credit balances are projections of ordered append-only ledger entries. Entries carry owner, sequence, type, signed balance effect, reason, idempotency key, actor and server timestamp, with optional purchase and AI-request references. Projection rejects duplicate entry/idempotency identity, ordering violations, cross-owner entries and debt-producing histories. AI credit use is represented as a server reservation; the client refuses offline reservation and never mints credits locally.

The Play restoration/reconciliation boundary is now implemented locally. The client can query platform-owned purchase references, collapse identical duplicate transactions and submit them with a unique reconciliation key to the trusted backend. Conflicting duplicate receipts fail before transport. Offline restore, cross-account results, invented processed transactions and backend failures return a non-destructive unavailable result; none can author an entitlement or credit balance on the device. Only a validated backend reconciliation result exposes the new server snapshot and balance.

A GetX plan-and-credits screen now presents active, offline-grace and unavailable access as distinct states, shows only the server-reported credit balance, exposes append-only credit reasons/effects, and provides an announced restore flow. Failed restoration retains the last verified entitlement and balance. The long layout is verified at 200% text scaling. Connectivity remains an injected platform state rather than a user-authored entitlement switch.

The authenticated shell now has an optional lazy Plan destination for this controller/screen. Product and paywall contracts separate remotely versioned identity, benefits, feature gates and display order from Google Play's localized price presentation. Products missing from the Play response remain unavailable; the app never fabricates a price. Duplicate remote or store product identities fail closed. A concrete remote-catalog adapter now loads the active version through the non-secret `ENTITLEMENT_CATALOG_URL`, fresh Firebase ID and App Check tokens, a 128 KiB response cap and bounded product/benefit/feature collections. Unknown product kinds, invalid subscription/credit combinations, malformed versions and insecure endpoints fail closed. Production activation still requires the live identity and deployed catalog endpoints.

The GetX paywall controller and responsive purchase screen are implemented locally. A purchase can be completed, pending, cancelled or failed at the Play boundary. Pending/cancelled results never reach reconciliation, and a completed result updates access only after the trusted backend returns a matching owner and processed transaction. Offline, unpriced and product-mismatched attempts fail without entitlement changes. The paywall explains that prices come from Google Play, disables unavailable products and is verified at 200% text scaling.

The official Flutter `in_app_purchase` 3.3.1 package now backs the first concrete Play adapter. It queries localized product details, listens to the purchase stream from adapter construction, maps purchased/pending/cancelled/error states, and collects restored purchases through Google Play's restoration stream with bounded quiet and total timeouts. It sends only server verification data into the trusted reconciliation contract and retains each platform purchase for completion only after the backend confirms that transaction as processed. Empty restoration returns an empty result and never fabricates access. Verified results can be applied to the owner-bound Plan & Credits controller; cross-owner results are rejected without replacing visible state. Android device/Play test-track verification remains deferred as directed.

The trusted billing client boundary is implemented behind the reconciliation contract. A non-secret `BILLING_BACKEND_URL` compile-time setting must resolve to HTTPS without embedded user info, query or fragment. Every request requires fresh injected Firebase ID and App Check tokens, includes an explicit idempotency key, and transmits only owner identity plus Play receipt references. Responses are capped at 256 KiB and strictly decoded into server-revisioned entitlement and balance results; missing credentials, HTTP failures and malformed payloads fail closed. No Firebase service-account or Play developer credential is stored in the app. Deployment and backend transaction processing remain external work.

Authenticated monetization composition is implemented as an owner-bound runtime factory. It starts one shared Play purchase listener, binds restore and purchase reconciliation to the stable verified UID, shares the resulting entitlement controller with the paywall, and rejects attempts to compose a paywall over another account's controller. Connectivity, idempotency generation, Firebase token providers, the published product-catalog gateway and backend endpoint remain injected production dependencies. The Plan screen exposes the paywall entry only when that factory is supplied; missing live configuration does not reveal fake plans or prices. The runtime exposes explicit disposal for account sign-out or switching. Production-root activation remains gated on the real identity and catalog adapters.

The last server-verified reconciliation result can now be retained in the encrypted, owner-specific Drift database and restored after restart. This cache is written only by a decorator around a successful trusted reconciliation, before Play completion; a mismatched owner is rejected. Server revisions cannot move backward and a different result cannot reuse the same revision. Cache records never enter the upload outbox because they are server-derived projections, not client-authored state. The account feature factory resolves the cache only through the stable authenticated UID, and billing composition uses it for the initial entitlement, informational balance and verified credit history. Offline credit reservation remains prohibited, so the cached balance cannot mint or spend credits.

Billing reconciliation responses now carry the bounded append-only ledger behind the visible balance. Every entry is strictly decoded with its sequence, type, signed effect, reason, idempotency identity, actor, server timestamp and optional purchase/AI reference. The existing projection rules re-check owner binding, sequence continuity, duplicate identities, delta direction and non-negative balance; the projected balance must exactly equal the server-reported balance before the result can be cached or rendered. Restore and purchase replace the visible history only with that validated ledger, and restart hydration reads the same encrypted record.

The server-authoritative AI credit-reservation client is now implemented through the non-secret `CREDIT_BACKEND_URL`. Composition binds it to the stable authenticated UID. The existing coordinator blocks offline requests before credential or transport work; online requests require fresh Firebase ID and App Check tokens, a bounded positive credit count and an explicit idempotency key. The response must be a newly reserved record matching the exact owner, AI request and credit count. Other states or mismatches fail closed. This client is deliberately not chained to Gemini as a sequence of independent client calls: settlement or release after provider execution must be atomic in the trusted backend before metered AI is activated.

A separate authenticated status-refresh path is implemented through `BILLING_STATE_URL`. It allows renewals, refunds, expiries and real-time developer notification results to reach the app without forcing a Play restore. The response uses the same strict entitlement/ledger decoder but must contain no processed purchase transactions and must match the active owner. When configured, the Plan screen offers an explicit refresh action and also refreshes when the app resumes or connectivity changes from offline to online. Concurrent triggers are coalesced and automatic triggers are throttled to one attempt per five-minute window; explicit user refreshes remain immediate. Offline or failed refresh retains the encrypted last-known-good state. Successful refresh replaces entitlement, balance and ledger together and passes through the rollback-safe encrypted cache.

Focused tests cover active/offline-expired entitlement behavior, feature gates, ordered ledger projection, balance mismatch/replay rejection, authenticated online-only reservation, explicit/resume/reconnect status refresh, automatic-trigger throttling and manual-refresh bypass, duplicate/conflicting receipt handling, owner binding, encrypted restart restoration, cache rollback/conflict rejection, empty and multi-purchase restoration, deferred Play completion, strict remote product configuration, trusted transport credentials and non-destructive failure. Static analysis is clean.

The paywall fails closed when either the trusted catalog or Google Play product lookup fails: it clears stale products, announces that no price was invented and exposes an explicit retry action. A successful retry replaces the failure state with newly loaded Play-backed prices; it never grants access or changes credits by itself.

The presentation boundary also catches a failed local application of an otherwise verified purchase result. It releases the in-progress UI state, makes no client-authored entitlement adjustment and directs the user to Restore Purchases so the trusted server result can be reconciled again.

Billing teardown is idempotent. Disposing the owner-bound billing feature stops the shared Google Play purchase listener, immediately releases pending purchase/restore callers with a safe failure and rejects any later adapter operation instead of leaving it to time out. This lifecycle must be invoked before an authenticated account runtime is replaced or discarded.

The owner-bound composition is terminal after disposal: it cannot create a new entitlement or paywall controller for the signed-out owner, and repeated disposal returns the same shutdown operation. This prevents a stale account scope from rebuilding UI against an already-closed Play listener.

Billing presentation failures emit only fixed, payload-free diagnostic categories through an injectable telemetry boundary. The event type system cannot carry owner IDs, purchase tokens, product IDs, prices, health content, exception text or backend responses. Catalog load, unavailable purchase, local result application, refresh, restore and cross-owner rejection paths are observable without weakening data minimization; the default sink records nothing until an approved production telemetry adapter is configured.

The authenticated billing composition accepts one telemetry sink and injects the same boundary into its owner-bound Plan and Paywall controllers. Production activation therefore has a single auditable configuration point, while tests and unconfigured builds retain the no-op default.

Every telemetry emission is best-effort and isolated behind a non-throwing recorder. An unavailable or defective diagnostics provider cannot change billing state, hide the intended user error, leave progress controls locked or prevent recovery actions.

Concurrent paywall catalog triggers are coalesced onto one active future. Every caller waits for the same trusted catalog/Google Play lookup, only one result can publish state, and a later retry starts only after the active load has fully settled. This prevents duplicate network work and stale-response replacement during rapid lifecycle or retry events.

An offline paywall performs no trusted-catalog or Google Play lookup, announces that current prices require connectivity and disables both retry and purchase actions. Existing products may remain visible for context but cannot be purchased offline. After a trusted connectivity transition, the user can explicitly retry and only fresh Play-backed pricing becomes actionable.

Connectivity transitions carry a local revision. If an already-running catalog request completes after the device has moved offline—or after any newer connectivity transition—its success or failure is discarded and cannot overwrite the current state or emit a misleading catalog-failure event. A fresh online retry is required before products become actionable.

Catalog freshness is bound to the exact connectivity revision that loaded it. Previously displayed products remain non-actionable after an offline/reconnect cycle, the retry action remains available even while those stale cards are visible, and both the UI and controller reject purchase initiation until a fresh trusted catalog/Play lookup succeeds.

Purchase initiation additionally requires the exact product instance from the current loaded catalog projection. A forged product or a card/reference retained across catalog reloads is rejected before the Google Play launcher is called, forcing selection from the latest trusted definitions and Play presentations.
